Bring a machine under governance. It works with IPv6 switched on — nothing to disable.

Ubuntu Server 24.04 or 26.04

  1. Install Ubuntu with your admin user and your SSH key (the installer offers "import SSH key from GitHub").
  2. On that machine, as the admin, run one command. It shows every change first if you add --dry-run. 
    curl -fsSLo niyantrak-bootstrap.sh <release URL> && echo "<sha256>  niyantrak-bootstrap.sh" | sha256sum -c && sudo bash niyantrak-bootstrap.sh
  3. It hardens remote login, locks root, turns on the firewall and audit rules, and refuses to lock you out.
  4. The machine appears under Fleet. Approve it there.

Windows 10 / 11 (developer laptops)

  1. Open PowerShell as Administrator.
  2. On the control machine, open Fleet and press Invite a machine. Copy the Windows line.
  3. Paste it into the laptop's PowerShell. It checks this panel's certificate and the script's fingerprint, then shows what it would change — nothing is changed yet.
  4. Run the same line again with -Apply at the end. It turns on OpenSSH Server (keys only), lets only the control machine connect, and asks for the join token.
  5. Keep IPv6 on. The laptop appears under Fleet; approve it there. Step-by-step and how to undo: docs/WINDOWS.md.

    A governance officer's routine, step by step. Each step names the screen that does it.

    Day 1 · set up (about an hour)
    1. The owner claims the panel with the one-time code shown on the control machine and sets a password (passkey optional).
    2. Owner invites the governance officer, an approver and an auditor — .
    3. Officer picks the laws that apply where you operate — . Starter rules appear.
    4. Officer reads each starter rule, tests it on a sample, adjusts the wording — .
    5. Approver approves the first rule book version; it starts being enforced on bots and AI agents.
    6. Operators add machines — ; developers register their laptops.
    Every week (30 minutes)
    1. Clear the approvals queue; reject anything without a reason — .
    2. Look at what was blocked and why; a rule that blocks good work gets a proposed change — .
    3. Check drift caught on machines and that each was reverted or approved.
    Every month
    1. Export the evidence pack (masked identifiers, routes, approvals, blocks, chain check) for leadership or your auditor — .
    2. Review roles: remove leavers, check no one holds conflicting roles.
    3. Review rule hits: rules never used, rules hit too often.
    When something goes wrong
    1. Switch the affected bot or agent to block in one click; personal data stops flowing.
    2. Use Activity (6W) to see who, which agent, what, where, why and which project — the chain shows nothing was edited afterwards.
    3. Export the incident evidence and follow your breach-notification duty (timelines differ by law — your legal adviser sets them).
    4. Fix the rule, test it, have it approved, re-enable.

    Every bot turn and agent action, chained so that any edit or deletion is detected. Export an evidence pack for your auditor.
