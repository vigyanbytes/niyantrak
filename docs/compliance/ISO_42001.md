# Niyantrak and ISO/IEC 42001 (AI management system)

> **Mapping only. No certification claim.** Niyantrak is not certified against ISO/IEC 42001, and using it does not
> certify your organisation. This page shows where Niyantrak's features can provide evidence for an AI management
> system. Not legal or audit advice.

## The standard in one paragraph

ISO/IEC 42001:2023 sets requirements for an **AI management system (AIMS)**: the policies, roles, risk process,
controls and records an organisation uses to develop, provide or use AI responsibly. Like ISO/IEC 27001 it has
management-system clauses (4 to 10) and a list of reference controls in **Annex A**. Organisations can be certified
against it by an accredited body.

**Source:** ISO/IEC 42001:2023, <https://www.iso.org/standard/42001>. The standard is a paid document. Control numbers
and titles below come from public summaries (for example ISMS.online's Annex A pages) and are **unverified against
the purchased text**; check them against your licensed copy.

## Management-system clauses

| Clause | What it asks (short) | Niyantrak | Status |
|---|---|---|---|
| 4 Context | Scope, interested parties, the AI systems in scope | As-built docs and signed node cards list machines; 5W `agent` and `route` fields show which AI agents and models are actually in use. | Partial (inventory input) |
| 5 Leadership | AI policy, roles, responsibilities | Decision log records policy decisions and who made them (OS identity). Roles: Commercial. | Partial |
| 6.1 Risk and impact assessment | Identify and treat AI risks; assess impacts | Data from the gate and 5W store (what was blocked, how often, which data types went where). The assessment is yours. | Partial |
| 7.2, 7.3 Competence and awareness | Trained people | Not addressed. | Yours |
| 7.5 Documented information | Control documents and records | Append-only decision log with derived status; as-built docs generated byte-identically from node cards (`niyantrak docs generate`). | Helps |
| 8 Operation | Run the planned controls | Agent gate enforces hard stops on AI coding agents. | Partial |
| 9 Performance evaluation | Monitor, measure, audit, review | `niyantrak telemetry ask` answers record questions with the SQL shown; `proof/` keeps test, coverage and leak-scan evidence per run. | Partial |
| 10 Improvement | Nonconformity, corrective action | Decisions can be superseded or retracted, never edited in place, so the history of a correction is kept. | Partial |

## Annex A reference controls

| Control | Title (short) | Niyantrak | Status |
|---|---|---|---|
| A.2 | Policies related to AI | Decision log holds policy decisions; commercial rule book holds rules in plain words with citations. | Partial / Commercial |
| A.3 | Internal organisation (roles, reporting concerns) | Identity from OS login. Roles, separation of duties: Commercial (in build). | Partial |
| A.4 | Resources for AI systems (data, tools, computing, people documented) | Signed node cards and as-built docs document machines; 5W shows agents and models used. | Partial |
| A.5 | Assessing impacts of AI systems | Facts for the assessment only. | Partial |
| A.6.2.6 | AI system operation and monitoring | Activity (5W) screen; gate decisions per agent and machine. | Partial |
| **A.6.2.8** | **AI system recording of event logs** | 5W events with hash-chained manifest (`niyantrak/telemetry/store.py`), gate decision log (`niyantrak/gate/events.py`), decision log. Logs hold labels and counts, never content. | **Helps** (for agent actions and governed data flows); gate log not hash-chained |
| A.7 | Data for AI systems (quality, provenance, preparation) | `niyantrak scan` finds identifiers in data before it is used. No provenance or quality checks. | Partial |
| A.8 | Information for interested parties | Not addressed (notices to users). | Yours |
| A.9 | Use of AI systems (responsible use processes, intended use) | Agent gate enforces "not allowed" uses for coding agents; commercial rule book compiles your use rules into agent policies. | Partial / Commercial |
| A.10 | Third-party and customer relationships (suppliers) | `where` / `route` fields record which model provider received each request. Supplier assessment is yours. | Partial |

## Evidence an auditor can see

| Ask | Show |
|---|---|
| "How do you log AI agent actions?" | `niyantrak gate status`, the gate JSONL log, rule ids in `niyantrak/gate/engine.py` |
| "Can logs be altered?" | `niyantrak telemetry verify`, `niyantrak decisions verify` |
| "Which AI systems and models are in use?" | `niyantrak telemetry ask` grouped by `agent` and `route`; as-built docs |
| "How do you keep personal data out of models?" | `niyantrak scan` output; commercial gateway evidence |
| "Is the tool itself tested?" | `proof/latest/` (junit, coverage, leak scan) |

## Limits

No AI policy templates, impact-assessment templates, Statement of Applicability or internal audit programme. Those are
yours to write; Niyantrak supplies evidence for some of them.
