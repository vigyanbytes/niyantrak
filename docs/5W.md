# 5W activity events

Niyantrak records activity as **5W events**: who acted, on whose behalf (whom), what kind of action, where the data
went, and why it was allowed or stopped, plus the agent, the route, the rule ids that decided it, the outcome and
per-type counts of personal data that was found. The panel's **Activity (5W)** screen is drawn from these events.

An event **never** holds message text, prompts, replies or identifier values. Personal data appears only as a count
per type (`"entity_counts": {"EMAIL": 2, "AADHAAR": 1}`).

Code: `niyantrak/telemetry/` — `schema.py` (validation), `sink.py` (OTLP/JSON in), `store.py` (Parquet + DuckDB).

## The event (`niyantrak.5w/1`)

| Field | Required | Type | Meaning |
|---|---|---|---|
| `ts` | yes | ISO 8601 or epoch seconds | when it happened (stored as UTC) |
| `who` | yes | label | the actor: a role or display label (`Priya (DevOps)`, `Clinic bot`) or a pseudonym `p-…` |
| `whom` | no | label | on whose behalf / whose data, as a category (`patient`, `customer`) |
| `what` | yes | label | kind of action (`Answer patient query`, `Open firewall port`, `chat`) |
| `where` | yes | label | where the data went (`Cloud`, `Local GPU`, a provider name) |
| `why` | yes | label (≤ 96 chars, ≤ 12 words) | the rule or reason (`RB-ROUTE-001 mask personal data`) |
| `outcome` | yes | enum | `allowed` `masked` `local` `blocked` `needs_approval` `approved` `rejected` `error` |
| `agent` | no | label | the AI agent or gateway (`Claude Code`, `WhatsApp gateway`) |
| `route` | no | label | the route or model the request took |
| `machine` | no | label | the machine it happened on (infrastructure governance chart) |
| `session` | no | pseudonym `p-<12 hex>` | groups events of one conversation; never the raw id |
| `rule_ids` | no | list (≤ 16) of short codes | `["RB-ROUTE-001"]` |
| `entity_counts` | no | `{TYPE: count}` (≤ 32 types) | how many identifiers of each type were found — counts only |
| `source` | no | `json` \| `otlp` | set by the sink |
| `event_id` | no | 32 hex | generated when absent |

A label is one line, at most 64 characters and 8 words. A label may be a real path — POSIX absolute (`/var/log`),
Windows drive (`C:\Users\Public`, `D:/data`) or UNC (`\\fileserver\share`) — and gets every other check: an email,
Aadhaar, card number or long digit run inside a path segment is still rejected, and shell punctuation
(`` ; | $ ` < > " ``) is never a path character.

### What validation rejects

- **Any field not in the table** — `message`, `text`, `body`, `prompt`, `content`, `customer_id`, … The error names the
  field, never the value.
- **Free text** — labels over the length/word limits, or with line breaks or unexpected characters.
- **Identifier values in any string** — every label, rule id and entity type is run through the same checksum-validated
  recognizers as `niyantrak scan` (Aadhaar, PAN, GSTIN, IBAN, card, email, phone, SSN, NINO, UPI, …). A hit rejects the
  event. Runs of nine or more digits are rejected as identifier-like.
- A `session` that is not already a pseudonym.

## Sink

```
niyantrak telemetry [--dir <store>] [--writer sink-1] sink [--bind 127.0.0.1] [--port 4318]
```

- `POST /v1/logs` — OTLP/HTTP logs, **JSON encoding** (`Content-Type: application/json`; protobuf gets 415). Reply follows
  OTLP: `{}` or `{"partialSuccess": {"rejectedLogRecords": n, "errorMessage": "…"}}`.
- `POST /v1/events` — one 5W event, a list, or `{"events": [...]}`. Strict: an event with a field outside the table is
  rejected (`400` when nothing was accepted).

The sink has no authentication; keep it on loopback or a private address.

### OTLP mapping

Record attributes win over resource attributes; the first non-empty key wins.

| 5W | OTLP attribute keys |
|---|---|
| `who` | `niyantrak.who`, `enduser.role`, `user.role`; else **pseudonym** of `enduser.id` / `user.id` |
| `whom` | `niyantrak.whom` |
| `what` | `niyantrak.what`, `gen_ai.operation.name`, `event.name` |
| `where` | `niyantrak.where`, `gen_ai.provider.name`, `gen_ai.system`, `server.address` |
| `why` | `niyantrak.why` |
| `agent` | `niyantrak.agent`, `gen_ai.agent.name`, `service.name` |
| `route` | `niyantrak.route`, `gen_ai.request.model` |
| `machine` | `niyantrak.machine`, `host.name` |
| `session` | **pseudonym** of `session.id` / `gen_ai.conversation.id` |
| `outcome` | `niyantrak.outcome` |
| `rule_ids` | `niyantrak.rule_ids` (string array) |
| `entity_counts` | `niyantrak.entity.<TYPE>` (int), e.g. `niyantrak.entity.EMAIL = 2` |

Missing values default to `who=unknown`, `what/where/why=unspecified`, `outcome=allowed`.

**Redaction:** the log body, `gen_ai.prompt`, `gen_ai.completion`, message content and every attribute not listed
above are dropped before validation (only counted). If an allowed attribute still carries an identifier value, the
record is rejected. Pseudonyms are `HMAC-SHA256(salt, id)` truncated to 12 hex characters; the salt is created
per store (`<store>/salt`, mode 0600) and never leaves the machine.

## Store

```
<store>/segments/<writer>/<YYYY-MM>/seg-<ns>-<rand>.parquet   append-only, one month per segment
<store>/manifest/<writer>.jsonl                              hash-chained: sha256 + rows per segment, prev = sha256(previous line)
<store>/view/events.parquet                                  materialized query view (rebuilt when the manifest changes)
```

Default store: `$NIYANTRAK_TELEMETRY`, else `<state root>/telemetry`. Each writer appends only to its own manifest.

- `verify` — broken manifest chain, missing segment, sha256 or row-count mismatch, Parquet files the manifest does
  not list. `materialize` and `compact` refuse to run on a store that fails it; the panel then says so instead of
  drawing charts.
- `compact` — monthly: merges one writer's segments of each month before the current one (or `--month YYYY-MM`) into
  one segment, records it with the files it replaces, then deletes them.

```
niyantrak telemetry ingest events.json     # append 5W JSON (exit 1 if any event was rejected)
niyantrak telemetry verify
niyantrak telemetry compact [--month 2026-09]
niyantrak telemetry activity --days 7      # exactly what the panel draws
```

Needs the optional extra: `pip install niyantrak[telemetry]` (pyarrow + duckdb). Without it the panel still runs and
shows sample activity.

## Panel

`GET /api/activity?days=7[&k=who|whom|agent|what|where|why|outcome|machine|route&v=<label>]` (days 1–90) returns:

```json
{ "empty": false, "days": 7, "from": "2026-10-17", "to": "2026-10-23", "total": 559, "filter": null,
  "sankey": { "nodes": [{"name": "Clinic bot", "col": "who", "value": "Clinic bot"}], "links": [{"source": "…", "target": "…", "value": 3}] },
  "week":   { "days": ["2026-10-17", "…"], "outcomes": ["masked", "blocked"], "series": [{"name": "masked", "data": [0, 0, 3, …]}] },
  "why":    [{"name": "RB-ROUTE-001 mask personal data", "value": 360}],
  "rules":  [{"name": "RB-ROUTE-001", "value": 360}],
  "infra":  { "hosts": ["edge-01"], "series": [{"name": "masked", "data": [3]}] },
  "by":     { "who": [...], "agent": [...], "what": [...], "where": [...], "why": [...] } }
```

The Sankey runs who → agent → what → where; a name that appears in two columns gets a `(column)` suffix so the flow
stays acyclic. When the store is empty or the extra is missing the reply is `{"empty": true, "reason": "…"}` and the
screen shows sample activity with the "Sample activity" note. The offline demo (`tools/build-demo.py`) always uses
sample data.
